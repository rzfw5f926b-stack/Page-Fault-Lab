# Codex總攬 測試需求：回歸組 T1～T5 K=3，關掉提示詞快取（Qwen3.6-35B-A3B，llama-server mmap）

2026-11-11 19:15～22:52，Mac mini（M6、32GB）。每次嘗試一行，在同目錄的 `reg_qwen3.6-35b-a3b_night5r.jsonl`（18 行）。原始紀錄在 Codex總攬 的 `exp/accept_results_k3_llama_qwen3.6-35b-a3b_night5r.txt` 和 `exp/llama_logs/` 同名目錄。

目的：驗證 Fable 第二次審查的推測——server 開久了變慢，是因為 llama-server 把提示詞快取放在記憶體（`--cache-ram` 預設 8192 MiB），佔用變大後把走 mmap 的專家權重擠出檔案快取。

## 和其他輪的差別

| | night3r | night4r | **night5r** |
|---|---|---|---|
| server 重啟 | 整輪不重啟 | 每題每輪之前重啟 | 整輪不重啟 |
| `--cache-ram` | 預設 8192 MiB | 預設 8192 MiB | **0（關掉）** |
| 呼叫方式 | `accept.sh` 一次跑完 K=3 | 每題每輪各呼叫一次（K=1） | 一次跑完 K=3 |

其他條件三輪相同：`RESIDENCY=1`、ctx 65536、`-b/-ub 512`、`exps=CPU`、單一 slot、output 上限 32768、worker 20 步、每次嘗試 3,600 秒、自動重試最多 2 次。和正式派工條件的差異同 `摘要_hard_qwen3.6-35b-a3b_night3.md` 開頭的表。

## 結論：推測成立，關掉快取後不會隨時間變慢

依 server log 每個請求的開機分鐘數和結束時 context 長度分組（`scripts/server_speed_ctx.py`）：

|---|---|---|---|---|---|

| 30～60 分 | <10k | 10.6 | 14.2 | 34 | 121 |
| ≥60 分 | <10k | 9.9 | **16.5** | 30 | **140** |

同一時段的資源（`logs/resources.csv`，每 30 分鐘平均）：

| | night3r | night5r |
|---|---|---|
| server footprint 最高 | 9.8GB（開機 30 分鐘後就到 9.3GB） | 3.7GB |
| 壓縮記憶體 | 6.3GB → 13.3GB | 3.2～5.8GB，沒有上升趨勢 |
| SSD 讀取 | 169 → 300～566 MB/s | 47～145 MB/s |
| 可用記憶體 | 57% → 35% | 58～67% |

night5r 的 server log 裡沒有任何「making room for prompt cache entry」（快取滿了刪舊的），night3r 從開機約 130 分鐘開始出現。

所以變慢的主因是提示詞快取佔的記憶體，不是 server 開了多久。這一輪跑了 3 小時 37 分，沒有重啟，速度一直維持在開機時的水準。**每題重啟（night4r）可以用 `--cache-ram 0` 取代**，而且同一題跑超過 30 分鐘也不會變慢，這是重啟做不到的。

關掉快取的代價：整輪讀提示詞共 180,841 token（304 個請求），night3r 是 169,946 token（360 個請求），沒有明顯多出要重算的量。單一 slot、一次只跑一題時，同一段對話的前綴快取在 slot 自己的 KV 裡，用不到 `--cache-ram` 那一層。

這只有一輪對照，但速度和記憶體的差別很大，而且和 night3、night3r 兩晚的趨勢都對得上。

## 失敗細節

- **T1 r1**：前 2 次測試都過，但改動超過 8 行被還原（同 night3r T1 r1），第 3 次在範圍內。
- **T5 r1 第 1 次**：用滿 20 步。最後一步是 opencode 到上限時強制模型停下，最後一句是「Let me fix `_load_inputs()` …」，還在動手，不算說完成。轉檔腳本原本因為最後一步的結束原因是 `stop` 而把它記成說完成，已修正：用滿步數上限也算步數用完。
- **T5 r1 第 2 次**：3,601 秒逾時。這次想得很多（output 34,422 token），只用了 10 步，context 長到 59,745，接近 65,536 的上限。逾時不會自動重試，這一輪算失敗。
- **T5 r2**：通過，但 context 峰值也到 59,739～60,052。T5 是回歸組裡最接近 context 上限的題目，放寬條件時要注意。
- 一次「排隊中的請求等 5 分鐘被取消」（開機第 33 分鐘，和 night3 H2 的 header 逾時同一種）：這次 opencode 重送後就恢復了，沒有影響結果。
