# Codex總攬 測試需求：回歸組 T1～T5 K=3，關掉標題請求後的驗證（Qwen3.6-35B-A3B，llama-server mmap）

2026-11-12 11:00～14:36，Mac mini（M6、32GB）。每次嘗試一行，在同目錄的 `reg_qwen3.6-35b-a3b_night7t.jsonl`（21 行）。原始紀錄在 Codex總攬 的 `exp/accept_results_k3_llama_qwen3.6-35b-a3b_night7t.txt` 和 `exp/llama_logs/` 同名目錄。

目的：驗證 Codex總攬 的修法。opencode 每次嘗試開頭會送一個產生標題的請求，它先佔住唯一的 slot，主請求就等不到 header（見 `摘要_reg_qwen3.6-35b-a3b_night6x.md`）。這次 `oc_llama.py`（Codex總攬 commit 4c2ed36、c70de89）關掉了標題請求（`agent.title.disable`），並把 `headerTimeout` 設成 7200 秒。

## 和 night5r 的差別

- 只差在 `oc_llama.py` 的這兩項設定，其他條件相同：`RESIDENCY=1`、`CACHE_RAM=0`、ctx 65536、`-b/-ub 512`、`exps=CPU`、單一 slot、output 32768、20 步、每次 3,600 秒、自動重試 2 次、整輪不重啟。
- **這次是白天跑**（使用者同意提早開跑）。期間同一台機器上有其他使用（含這個 Claude Code session）。

## 結論：修法有效

| 檢查 | 結果 |
|---|---|
| opencode 紀錄裡的 `Timed out waiting for response headers` | **0 次**（night6x 3 次、night3 1 次） |
| server log 的 `cancel task` | **0 次** |
| 提示詞約 500 token 的短任務（標題請求） | **0 個**。161 個任務裡，除了開頭 1 token 的探測，最短的提示詞是 2,175 token，而且每次嘗試都是從這裡開始一路變長（2,175 → 4,707 → 5,318 …），是主請求的對話 |
| 同一個資料夾的下一次 `opencode run` 卡在啟動 | **沒有**。21 次嘗試的時間加起來是 12,238 秒，整輪 12,960 秒，差 722 秒，平均每次 34 秒，花在還原檔案和跑驗收上 |

另外，主請求第一步的提示詞約 2,200 token，比以前判斷主請求時用的「至少 6,000 token」小很多。原因沒有查。之後用提示詞長度判斷哪個是主請求時，要先看那一輪自己的數字。
